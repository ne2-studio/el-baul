# Design Language

El Baúl is warm, intimate and deliberately non-technical: a private family archive, not
a cloud storage dashboard. The visual language comes from the current implementation in
`app/src/styles/theme.css`, `app/src/styles/fonts.css`, `app/src/styles/index.css`,
the design-system components, and the product/design guidance in `docs/DESIGN.md`.

Use this page as the design-language map before inventing new visual treatments. It
documents what exists today; it does not introduce a new token system.

### Color Usage

- Use `bg-background` for screens and `bg-card` for lifted content areas.
- Use `text-foreground` for primary text and `text-muted-foreground` for metadata,
  helper text, timestamps and secondary explanations.
- Use `bg-primary text-primary-foreground` for the single highest-priority action in
  a screen or modal.
- Use `bg-secondary`, `hover:bg-secondary`, `bg-muted` and low-opacity primary fills
  such as `bg-primary/10` for quiet affordances.
- Use `text-destructive`, `bg-destructive/8` and `border-destructive/20` for warnings
  and destructive confirmation context.
- Do not add cold raw palette colors for normal UI. Existing raw green/blue/purple
  avatar/status accents are exceptions in feature code, not general-purpose brand tokens.

- Do not use Lora for buttons, labels, helper text or dense controls.

## Spacing And Layout

Spacing is Tailwind's 4px-based scale. The recurring product rhythm is narrow,
mobile-first and spacious: 24px page padding, 12-16px control gaps, and 24-32px
section gaps.

### Spacing Usage

- Use `PageContainer` for top-level screen width and horizontal rhythm.
- Use `px-6` for page gutters and `py-5` for sticky headers.
- Use `gap-2` for tight icon/text pairs, `gap-3` or `gap-4` for controls and cards,
  and `space-y-6` or `py-8` for major screen sections.
- Use `max-w-md` for focused forms and empty states; use `max-w-[62rem]` for screens
  that can show multi-column cards on desktop.
- Do not create a new page wrapper unless `PageContainer` cannot express the layout.

## Shape, Radius And Surfaces

The shape language is soft and enclosing. The root radius is `1rem`, with derived
Tailwind theme radii for `sm`, `md`, `lg` and `xl`; component usage commonly reaches
for `rounded-xl`, `rounded-2xl`, `rounded-3xl` and `rounded-full`.

<div className="grid gap-4 md:grid-cols-4">
  <div className="bg-card border border-border rounded-xl p-4 text-sm">rounded-xl<br /><span className="text-muted-foreground">buttons, inputs</span></div>
  <div className="bg-card border border-border rounded-2xl p-4 text-sm">rounded-2xl<br /><span className="text-muted-foreground">cards, dialogs</span></div>
  <div className="bg-card border border-border rounded-3xl p-4 text-sm">rounded-3xl<br /><span className="text-muted-foreground">large sheets, icon blocks</span></div>
  <div className="bg-card border border-border rounded-full p-4 text-sm text-center">full<br /><span className="text-muted-foreground">avatars, FABs, pills</span></div>
</div>

### Shape Usage

- Use `rounded-xl` for inputs, compact controls and action buttons.
- Use `rounded-2xl` for cards, modal panels and message bubbles.
- Use `rounded-3xl` for larger hero/icon blocks and large bottom sheets.
- Use `rounded-full` for avatars, role badges, icon buttons and FABs.
- Do not mix sharp-cornered elements into product screens.

## Elevation And Overlays

Depth is soft and low contrast. Resting surfaces use white cards, low-opacity warm
borders and subtle shadows; high-priority floating actions use a warmer terracotta
shadow defined inline in `FAB.tsx`.

### Elevation Usage

- Prefer `shadow-sm` and `shadow-md` over heavy chrome.
- Pair elevation with `border border-border` when a white surface needs definition.
- Use translucent overlays such as `bg-background/80`, `bg-foreground/40` or
  `bg-black/50` depending on context: app chrome, warm product sheet, or media viewer.
- Use `backdrop-blur-sm` for sticky headers and soft blocking states.
- Do not use crisp gray shadows or high-contrast borders as the default way to separate UI.

- Use `transition-colors`, `transition-opacity`, `transition-transform` and

- Keep motion under about 300ms unless it represents ongoing progress.
- Do not add decorative animation that distracts from photos, memories or form input.

## Forms And Input Language

Form controls are soft white or beige surfaces with rounded corners, low-opacity borders
and terracotta focus rings.

<div className="max-w-md rounded-2xl bg-card border border-border p-6 space-y-5">
  <Input label="Nombre del baúl" placeholder="Familia García" value="" onChange={() => {}} helperText="Usa un nombre familiar y reconocible." />
  <div>
    <label className="text-xs text-muted-foreground uppercase mb-1.5 block">Decision reversible</label>
    <SelectionRow selected>
      <span className="text-sm text-foreground">No me acuerdo</span>
    </SelectionRow>
  </div>
</div>

### Form Usage

- Use labels above fields, helper text below fields, and `text-muted-foreground` for explanations.
- Use `focus:ring-2 focus:ring-ring` or `focus:ring-primary/30` for focus.
- Use `bg-input-background` or `bg-card` for normal fields, `bg-secondary` for fields inside
  large sheet forms where the surface is already card-colored.
- Use explicit destructive context blocks before irreversible textareas.
- Do not hide domain uncertainty; controls like "No me acuerdo" are valid product language.

## Empty And Supportive States

Empty states should feel like an invitation to contribute, not a dead end.

<EmptyState
  title="Sin fotos todavía"
  subtitle="Sube tus primeros recuerdos para empezar a llenar este baúl."
  icon={<Icon icon={icons.bookImage} size="xl" aria-hidden />}
/>

### Empty State Usage

- Use a muted low-opacity icon, a short Lora heading and muted explanatory copy.
- Prefer copy that suggests the next meaningful family action.
- Use generous vertical space (`py-16`) so empty states feel calm instead of cramped.
- Do not treat empty states as errors unless the user is blocked by a real failure.

## Breakpoints And Responsive Behavior

The app is mobile-first. The main explicit breakpoint used by design-system primitives is
Tailwind's `md` breakpoint (`768px`): large bottom sheets become desktop side drawers,
small confirmation sheets may center, media navigation controls become visible, and some
content grids expand.

Storybook exposes three stable viewports for visual review and regression tests:

| Viewport | Width | Why it exists |
|---|---:|---|
| El Baul mobile | 390px | Primary phone layout: bottom sheets, stacked content and compact tab bars. |
| El Baul narrow | 700px | Below `md` but wider than a phone: exposes max-width, overflow and tablet-like narrow behavior. |
| El Baul desktop | 1280px | Above `md`: side drawers, centered dialogs, visible media navigation and distributed tabs. |

### Existing Responsive Rules

- `md` is `768px`, inherited from Tailwind. Below it, components should be treated as
  phone or narrow layouts.
- `PageContainer` is always centered with `px-6`; its width stops growing at `62rem`.
- `BottomSheetModal size="lg"` is a bottom sheet below `md`, then a right-side drawer at
  desktop (`md:w-1/3`, full height, rounded left edge).
- Compact `BottomSheetModal` instances remain bottom sheets unless `desktopCentered` is
  set; then they become centered dialogs at `md`.
- `PhotoStage` hides side previous/next buttons below `md`; desktop reveals them.
- Tab bars in baul/chapter/person screens use `w-max` below `md` and `md:w-full` above it,
  so narrow screens scroll horizontally instead of wrapping.
- Chapter cards use `grid-cols-2 sm:grid-cols-3`; this is a `sm` change, while tab
  distribution remains controlled by `md`.

### Responsive Usage

- Build mobile layout first with full-width controls and bottom sheets.
- Use `md:` only when the desktop behavior genuinely improves repeated use or scanning.
- Keep screen content centered with `PageContainer`.
- Let horizontal tab bars scroll with `overflow-x-auto scrollbar-hide` instead of wrapping.
- Do not introduce dense desktop-only dashboards in the consumer app unless the product need
  is explicitly operational rather than family-memory oriented.
